# Backblaze B2 development backup setup

The user selected B2 and approved the project-local age v1.3.2 tool. This first step creates an empty private destination only; automatic backups, real recovery keys, uploads, lifecycle deletion and scheduler activation are not enabled.

## 1. Account

Open [Backblaze B2](https://www.backblaze.com/cloud-storage), sign up or sign in, and enable B2 Cloud Storage. Keep account credentials private. Check the account's actual free storage allowance and usage; the free allowance is shared across the account, not reserved for each bucket. Do not authorize a paid upgrade on this project's behalf.

## 2. Private development bucket

In **B2 Cloud Storage → Buckets → Create a Bucket**:

- Choose a unique, non-sensitive development name such as `fmv-backup-dev-<unique-suffix>`.
- Select **Private**.
- Do not enable Object Lock or automatic lifecycle deletion yet; the reviewed retention workflow will control backup expiration.
- Create the bucket, then note its bucket name and displayed **S3 Endpoint** privately. Use the actual endpoint shown by B2, not a typed example.

These steps follow [Backblaze's bucket guide](https://www.backblaze.com/docs/cloud-storage-create-and-manage-buckets). No real records should be manually uploaded during setup.

## 3. Stop at bucket ready

Reply **“bucket ready”**. Do not send keys, passwords, account IDs or screenshots containing credentials. Application-key scope and private local configuration will be configured when the destination adapter is ready. The integration will use a standard bucket-restricted application key, not the master key; see [B2 application-key documentation](https://www.backblaze.com/docs/cloud-storage-application-keys).

The account/bucket setup does not establish that 90 days of recovery points fit. A rough planning example is about 13 GB for 13 weekly full copies of a 1 GB vault, before database and encryption overhead. Capacity and spending behavior must be checked before enabling uploads; the retention window will not be shortened silently.

## Encryption tool verification

The standalone age release is checksum-pinned in `infra/ci/tools.lock.json`. The archive is cached under ignored `.local/ci-tools`; the existing tool helper extracts private temporary executables and removes them after each operation. There is no global installation or app package dependency.

`node infra/scripts/verify-backup-encryption.mjs` verifies the version, encrypts/decrypts a synthetic fixture and confirms modified ciphertext is rejected. Temporary test identities are removed; no real recovery identity is generated by this command. Real recovery-key custody and authenticated completion manifests remain required before real backups.
