# SHARE-02 — temporary external links readiness

Next ready roadmap area after summary and selected-original ZIP exports. Canonical authority: `docs/domains/sharing.md`, `docs/domains/access.md`, `docs/security/access-control.md`, F-05 in UX flows and sharing screen specification. Existing caregiver invitation links are not anonymous document-share authorization and must remain separate.

A recipient link would confer access outside the authenticated caregiver grant workflow, so existing independent Export or Manage permissions cannot silently be interpreted as authority to grant it. Issuer/revoker authority was explicitly approved on 18 November: owner only initially, delegate sharing deferred. Recipient access/lifecycle was then explicitly approved: originals-only bearer access, mandatory owner-chosen expiry up to7days, and permanent invalidation after Trash/Restore or source change. No separate recipient account/passcode is required.

Requirements to preserve in the eventual bounded implementation: explicit patient and exact selected sources, owner-chosen scope/expiry, revocation and access events, opaque high-entropy tokens stored only as hashes, no token/content in URLs logged by infrastructure or analytics, token confidentiality through recipient flow and referrer controls, current source/lifecycle validation on every access, no listing/enumeration and no long-lived provider URLs. Expired/revoked/source-invalid links stop future serving; downloaded bytes cannot be recalled. Keep private original and summary export semantics independent. Broader recipient verification, download permission, content scope, expiry bounds, token transport and abuse controls must be resolved against canonical specifications before exposing an anonymous endpoint.

Authorized independent groundwork: inspect existing access-link/token/session primitives and reusable source authorization/expiry/audit boundaries, document the threat model and design options. Do not enable a hosted public route, create real share tokens, expose records, or apply a migration based only on this readiness note. Any reviewed hosted migration/deployment retains its separate approval gate.


## Groundwork findings

Existing invitation tokens use 32 cryptographically random bytes encoded as43-character base64url with SHA-256-only persisted lookup. Existing proposal expiry is1–168hours, providing an implementation precedent but not recipient-link policy approval. Reuse cryptographic primitives where appropriate, while keeping invitation/account grants and anonymous document-link authority in distinct stores/endpoints. Token length/format is not proof of authority; lookup, current owner, expiry, revocation and exact source lifecycle must all remain authoritative.

The current application mounts the authenticated AuthRoot around the vault. An eventual external recipient view needs a deliberately isolated entry before that boundary, with no patient selector, vault navigation, account content or background private API requests. Keep the secret in an incoming URL fragment, remove it from browser history immediately and submit it only in a bounded body over the configured same-origin HTTPS service. Do not put tokens in request paths/query strings, logs, analytics, referers, persistent browser storage, public object URLs or automatic third-party previews. Do not alter existing invitation/hash authentication routing to masquerade a shared document as an authenticated patient context.

Planned store design must bind a token hash to the exact selected originals/source versions, not a live whole-patient/category query. Every recipient retrieval must revalidate the entire selection and current source lifecycle under the same patient/source guards used by original exports; a missing/invalid source must not produce a silently widened or partial share. Owner revocation and audit must be atomic. Creation retry must not mint duplicate untracked grants or pretend a hash-only secret can be recovered: define explicit one-time secret display and revoke/recreate handling before implementation. All network/byte/query work requires independent resource and abuse limits; invalid/expired/revoked lookup should reveal no patient/source existence.

No temporary-link runtime routes, tokens, database schema or external record exposure have been introduced. The recipient-access/lifecycle decision is approved; proceed with the bounded owner-only link ledger/source guards and tests, then obtain separate approval for any hosted schema write.
