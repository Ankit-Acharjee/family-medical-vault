# MED-01/MED-02 — owner prescription source choices

Added GET `/api/patients/:patientId/medication-reconciliations/source-options` for owner-only reconciliation candidate selection. It returns literal owner-attested source blocks with exact document/source/review/lifecycle bindings and document titles, without inferring current/historical medication status. Discovery examines at most 25 recent eligible documents, returns at most 50 unique choices and reports authorized overflow. Current source projection is shared with reconciliation freshness checks to avoid divergent eligibility rules.

The canonical patient lock precedes sorted document locks. Owner/current document authorization precedes clinical fields; original availability, extraction SHA/revision/lifecycle and latest attestation SHA/revision/lifecycle must all match. Withdrawn, stale and restored sources supply no choices until explicitly reviewed again. Document read audits contain no medical field values and final owner authorization follows audit. Delegates cannot call this owner-write-choice endpoint; their existing source/document access and read-only medication list policy are unchanged. Unsupported query keys fail explicitly.

Validation: full 352 server API/contract checks passed; focused disposable PostgreSQL clinical/medication lifecycle passed, including actual 26-document and 50-choice overflow cases, duplicate choice keys, owner/delegate denial, withdrawal and Trash/Restore invalidation, plus all existing reconciliation/CAS/history/audit checks. Workspace typecheck, server/contracts build, lint, formatting, OpenAPI and secret checks passed. No migration, dependency or hosted write was needed. Supervisor implementation/review; native workers/Astra remain quota-limited and no external fallback was used.

Changed: shared medication reconciliation contracts, reconciliation controller/service, API/contract tests and clinical/medication database fixtures. No frontend write form is enabled yet. The user is deciding exact-source duplicate identity (reuse the existing record with preserved history, or allow explicitly separate records). The forthcoming creation/correction interface must enforce that answer before enabling writes; matching names across prescriptions are never automatically merged.
