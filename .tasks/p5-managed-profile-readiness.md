# AUTH-03–AUTH-05 / AUTH-07 — Managed identity readiness

Current implementation creates exactly one owned Person per verified provider account. `persons.owner_account_id` is non-null/unique, personal onboarding is retry-safe, and records/storage namespaces are already Person-bound. Existing caregiver invitations grant access; they do not activate or transfer Person ownership. Do not reuse them as activation capabilities or make a second personal Person for a managed claimant silently.

Approved product authority: a verified user with an existing personal profile may create an unowned managed Person and receive explicit five-action patient-wide caregiver grants. Existing owner-only clinical/emergency policies must remain explicit; a creator grant must not impersonate Person ownership or silently expand those policies. Creation of credentials and public exposure remain prohibited.

Implemented foundation (see delivery report): introduce a nullable owned/unowned distinction, private managed-profile creation with retry identity and atomic explicit caregiver grant/audit, stable Person/storage identity, and current-principal authorization for every operation. Audit all nullable-owner consumers and raw SQL; shared document operations may use explicit grants, but owner-only operations must deny unowned profiles. Account onboarding still returns its one actual owned personal Person and must never claim an arbitrary managed profile by name. No DOB uniqueness, global duplicate search or account enumeration.

Activation is a separate security-sensitive operation, not a side effect of profile creation or invitation acceptance. Before its implementation, resolve issuer authority, independent authenticated claimant confirmation, final approval authority, competing claims/expiry/replay, preexisting personal-Person ambiguity and credential-deactivation behavior. Bind a domain-separated hashed single-use activation capability to exact managed Person, issuer and claim transition. Preserve Person IDs and originals. Never automatically merge an already-owned Person, copy records between identities, or select an identity by name/DOB.

Testing boundary: failed creation rolls back Person/grant/audit; same request retries one identity; denied/malformed/expired scopes cannot create or claim; retained authorization remains exact through ownership activation and no owner-only path opens while unowned. Activation races/replay/revoke require independent native database tests across instances. Exposed UI must show caregiver versus owner status and explain unresolved activation without implying that credentials were created. Hosted schema changes need separate approval after local review/tests. No managed-profile code/schema changes introduced by this readiness document.
