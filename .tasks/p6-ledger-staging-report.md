# DEL-03 / BACKUP-04 — immutable encrypted event staging

User decision, 23 November: reuse the existing verified development age public recipient. Canonical operations documentation records this choice. No real recipient pin, private recovery identity, signing key or hosted staging activation was read/generated/applied by this implementation.

Migration34 adds an empty development public-recipient policy catalog and immutable encrypted-publication rows. The standalone fixed-order UTF8 envelope binds format, environment, ledger ID, recipient fingerprint and exact authoritative event metadata, without inventing a sequence or current head. SQL independently re-derives the payload digest and computes ciphertext byte count/hash. Source/policy FKs restrict deletion; stored policy context and original ciphertext survive default rotation. Concurrent valid encryptions return one committed winner through separate READ COMMITTED statements. A retry must match the persisted policy and payload digest; after rotation the operator retrieves the old row and uses its original pin.

`fmv_app` cannot read the policy/artifact tables, stage ciphertext or alter artifacts. The separate capability role is NOLOGIN and receives no active operator membership. An existing capability with unsafe attributes/memberships fails review rather than being trusted. PG16+ automatic creator ADMIN-only membership is allowed with INHERIT/SET disabled. Policy metadata is immutable except the operator-controlled enabled flag; catalog starts empty. The trusted stager, not the database, is responsible for actually encrypting the canonical payload for the pinned recipient: an age header plus digest alone is not cryptographic proof of plaintext/recipient binding.
