# P3 disabled external-processing consent boundary

- Implements AI-04 / SEC-07 as a backend-only consent foundation. The explicit Person owner with current scoped View may read consent/history, record consent or withdraw the current grant. Delegates cannot act or read consent metadata. User-approved scope binds the exact document/original SHA, saved-text revision (0 when absent), lifecycle epoch, provider/policy version, purpose, categories and explicit finite owner-chosen expiry. Saving text, Trash/Restore, expiry or provider-policy retirement invalidates prior consent. No earlier grant becomes effective by fallback.
- One immutable revision stream and one current consent intent per document; a later grant replaces the prior intent. Withdrawal preserves the immediately preceding grant's historical binding even if expired, source-invalidated or policy-retired, while authenticating against today's accessible document. Contiguous revision/CAS, historical nonce fencing, canonical ordered fingerprints, category-order-insensitive exact retries, final owner recheck, source row locks and atomic content-free audit protect transitions. A source-stale grant replay conflicts; a grant acknowledgement proves historical recording, never processing authorization.
- Migration18 `20261115000400_processing_consent` introduces an empty infrastructure-reviewed policy catalog and append-only consent ledger with FORCE RLS. Runtime has catalog SELECT only and ledger SELECT/INSERT only. Catalog versions/generations cannot be reused or re-enabled after retirement, and deletion is prohibited; this prevents A→B→A revival. SQL guards enforce owner, ready/non-Trash source, exact current extraction/epoch, bounded expiry/purpose/categories, approved policy generation, contiguous revisions and exact withdrawal binding. Ledger follows document deletion cascade. No provider is seeded or enabled, and all earlier17 migration files remain unchanged.
- API: owner-only GET/PUT `processing-consent`, POST `processing-consent/withdraw` and bounded GET `processing-consent/history?beforeRevision=N` under existing document routes, sessions, CSRF and no-store boundary. Current result explicitly returns `externalProcessingEnabled:false` even for synthetic effective consent. Production catalog is empty, so grants are unavailable. No outgoing transport, provider SDK, environment activation switch, external document request, new dependency, consent UI or unrelated screen change was added.

Astra independently reviewed architecture and actual code, identified property-order-dependent fingerprints and catalog-dependent withdrawal, then confirmed both fixes and no remaining material findings for this disabled slice. Root owns schema/authority/integration and reviewed all changes. Native worker reset had passed; OpenCode was not used.

- Limits/release gates: backend only; no claim of hosted authenticated consent flows or provider integration. Before any adapter, implement a submission gate that safely orders dispatch against concurrent consent withdrawal/provider retirement, vet provider privacy/training/retention terms, verify infrastructure policy publication with production roles, and implement applicable processor-side deletion handling. Critical consent-history retention/purge and future delegate consent remain separate policy work.
