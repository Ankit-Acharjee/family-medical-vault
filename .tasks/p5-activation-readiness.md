# AUTH-04–AUTH-05 / AUTH-07 — Activation boundary

Managed creation `0a662b8` establishes a separate unowned Person and caregiver grants; it does not activate a login. Existing account onboarding creates a personal Person, so activation must be deliberately handled after verified sign-in but before ordinary personal onboarding. Otherwise a new claimant would acquire an unrelated personal identity before claiming the managed one. Existing owned-Person accounts require explicit reconciliation; no automatic merge, document copy, name/DOB matching or Person ID replacement.

Approved policy: explicit issuer approval of the verified claimant; deferral of already-owned identities; initial issuer restricted to the original managed-profile creator with current patient-wide View and Manage. Do not implement transfer based on raw Manage alone or assume a bearer invitation/secret establishes identity.

Implementation plan: separate hashed, domain-separated, expiring single-use activation capability, exact managed Person and creator identity, private authenticated inspection/claim, distinct creator approval, one-way ownership transition with current checks under account/patient locks and exact replay identity. Never reuse external document-sharing capabilities or mutate existing caregiver invitation states. No activation secret in paths/query/logs/browser storage; strip incoming fragments immediately, show scope and claimant reference only to authorized participants. Secret possession permits a pending claim, never ownership or access grants.

New verified claimants may need an application account without an owned Person. Reuse the existing verified session principal; do not manufacture provider IDs or credentials. Only approved activation may attach that account to the existing Person. `PersonStore.find/create` must continue to return the actual owned Person afterward. A competing ordinary onboarding operation must serialize with approval and fail safely rather than allow two identities/owners. Unique owner constraints and no raw runtime owner-update privilege remain required; any narrow transition needs SQL guards and explicit hosted migration approval.

Prove expiry/revoke/replay, competing claimants, creator lost access, account already owns a Person, onboarding-versus-approval races, audit rollback, exact old Person/document/storage identity and unchanged caregiver grants. Unknown/missing/nonexistent secrets or identity conflicts must not enumerate accounts or patients. Keep login deactivation distinct from profile deletion. No activation runtime routes, ownership mutation, token or hosted write has been introduced by this readiness note.
